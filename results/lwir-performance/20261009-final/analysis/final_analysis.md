# LWIR 영상 송신 성능 평가 결과

## 실험 구성

- 입력: `seq_001`, 16-bit PNG 971장, 640×480, 30 FPS
- 전송: H.264 (`x264enc`) → RTP/UDP → Ubuntu PC
- 반복: B0/Q1/E1/E2/B1 각 3회, 총 15회
- B0 세 번 중 두 번은 기존 유효 측정 결과를 재사용했다.
- 통계는 초기 60프레임을 제외한 각 실행의 평균/P95를 구한 뒤 3회 평균했다.

## 핵심 비교

| 지표 | B0 | B1 | 변화 |
|---|---:|---:|---:|
| Encoding 평균 | 1633.64 ms | 3.48 ms | 99.79% 감소 |
| Encoding P95 | 1705.28 ms | 4.51 ms | 99.74% 감소 |
| 송신 FPS | 30.00 | 30.00 | 유지 |
| 수신 FPS | 30.02 | 30.01 | 유지 |
| 송신/디코드 프레임 차이 | 0.24% | 0.00% | 개선 |
| Raspberry Pi CPU | 282.67% | 59.67% | 78.89% 감소 |
| Raspberry Pi 최대 RSS | 177.13 MiB | 83.78 MiB | 52.70% 감소 |
| RTP 비트레이트 | 52.22 kbps | 228.87 kbps | 338.29% 증가 |

B1은 독립 실험에서 개선이 확인된 `tune=zerolatency`와
`speed-preset=ultrafast`만 조합했다. Q1은 포함하지 않았다.

## 단계별 B0/B1 지연

| 단계 | B0 평균 | B0 P95 | B1 평균 | B1 P95 |
|---|---:|---:|---:|---:|
| Capture processing | 13.45 ms | 22.19 ms | 10.05 ms | 10.10 ms |
| Preprocess queue wait | 0.823 ms | 4.478 ms | 0.023 ms | 0.028 ms |
| Preprocess processing | 0.462 ms | 0.620 ms | 0.449 ms | 0.450 ms |
| Streaming queue wait | 0.226 ms | 1.165 ms | 0.042 ms | 0.046 ms |
| Streaming submit | 0.963 ms | 4.036 ms | 0.178 ms | 0.187 ms |
| Encoding | 1633.64 ms | 1705.28 ms | 3.48 ms | 4.51 ms |

가장 큰 병목은 전처리가 아니라 x264 인코더의 내부 프레임 보류였다.

## 조건별 해석

### Q1 — Queue Depth = 2

- 인코딩 평균은 1633.27 ms로 B0와 사실상 같았다.
- 세 번 모두 queue policy drop은 0이었다.
- 생산자가 소비자보다 지속적으로 빠른 상태가 아니어서 애플리케이션 큐가
  누적되지 않았다. 따라서 큐 깊이 제한만으로는 병목이 해결되지 않았다.

### E1 — `tune=zerolatency`

- 인코딩 평균은 33.99 ms, P95는 42.83 ms였다.
- x264의 look-ahead와 내부 버퍼링을 줄여 프레임을 오래 보류하는 현상을
  제거했다.
- CPU는 313%로 B0보다 10.73% 증가했고 RTP 비트레이트도 89.72 kbps로
  증가했다. 지연 감소와 압축 효율/연산량 사이의 상충관계가 나타났다.

### E2 — `speed-preset=ultrafast`

- 인코딩 평균은 200.90 ms, P95는 200.99 ms였다.
- CPU는 58.0%로 B0보다 79.48% 낮았다.
- 복잡한 움직임 탐색과 압축 결정을 줄이므로 처리량과 CPU는 개선되지만,
  단독 사용 시 look-ahead 버퍼가 남아 E1보다 지연이 컸다.
- RTP 비트레이트가 4.45 kbps로 매우 낮았지만 세 번 모두 971/971프레임이
  디코드되고 971개의 인코딩 측정 행이 생성됐다. 이 값은 해당 열영상
  시퀀스의 높은 프레임 간 유사성과 E2 단독 설정에서 관측된 결과로 한정한다.

### B1 — E1 + E2

- `zerolatency`가 내부 대기를 제거하고 `ultrafast`가 프레임당 계산량을
  줄이면서 평균 3.48 ms, P95 4.51 ms를 달성했다.
- 세 번 모두 송신 971, 디코드 971, queue drop 0이었다.
- RTP 비트레이트는 228.87 kbps로 증가했다. 초저지연과 낮은 CPU 사용량을
  얻는 대신 압축 효율을 희생한 결과다.

## E2E 제한

E2E Latency는 최종 성능 수치에서 제외했다. B0 최종 녹화 실행에서 RTP
메타데이터와 디코더 PTS가 124/968프레임만 매칭됐고, B1에서는
2/971프레임만 매칭됐다. 시계 동기화 여부와 별개로 프레임 대응 관계가
검증 기준 95%를 충족하지 못했다.

따라서 프레임 손실은 잘못된 메타데이터 기반 frame ID가 아니라
`송신 성공 프레임 수 - 디코드 프레임 수`로 계산했다. 단계별 지연,
FPS, CPU, 메모리, RTP 비트레이트는 이 매칭 문제와 무관하게 사용할 수 있다.
